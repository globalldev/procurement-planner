# Система планирования закупок (импорт из Китая, плечо 4–6 мес.)

Ты — ИИ-агент отдела закупок. Твоя работа: по свежей выгрузке ERP пересчитать план закупок,
проверить результат на здравый смысл, объяснить рекомендации закупщику и обновить дашборд.

## Главный принцип
**Числа считает код, а не модель.** Прогноз, остатки, даты и объёмы заказов — только из
`python -m planner`. Ты не пересчитываешь их в голове и не «подправляешь» руками. Если
рекомендация кажется неверной — ищешь причину в данных или параметрах, меняешь `config.toml`
(с объяснением) или код, перезапускаешь расчёт.

## Структура
- `config.toml` — все параметры политики (порог наценки 25%, плечо, уровень сервиса, цикл заказа…). Никаких констант в коде.
- `planner/data.py` — загрузка CSV, приём нового zip из `data/inbox/`, дата среза, проверка выгрузки (`DataError`).
- `planner/forecast.py` — спрос = уровень × сезонный индекс; месяцы дефицита исключаются (продажи ≠ спрос).
- `planner/policy.py` — дневная проекция остатков с заказами в пути, календарь заказов, страховой запас, кратность.
- `planner/engine.py` — сборка по всем SKU, статусы, риски, агрегаты, качество данных.
- `planner/backtest.py` — проверка прогноза на истории от нескольких точек отсчёта против «среднего за 12 мес» и «год назад».
- `planner/report.py` — `out/plan.json`, `out/plan.xlsx`, снимок на каждую выгрузку (`out/history`), сравнение с прошлой выгрузкой.
- `planner/brief.py` + `prompts/buyer_brief.md` — ИИ-сводка закупщику через `claude -p`, сверка её чисел с расчётом.
- `planner/publish.py` — публикация дашборда (commit и push только `docs/`) и уведомление.
- `tests/` — тесты расчёта на синтетической выгрузке: `python -m pytest tests`.
- `dashboard/template.html` → `docs/index.html` (один статический файл, данные внутри).
- `scripts/daily.ps1` — ежедневный цикл; `scripts/install_schedule.ps1` — задача в Планировщике Windows.

## Команды
- `python -m planner all` — полный цикл: данные → расчёт → бэктест → Excel → ИИ-сводка → дашборд → **публикация**
  (commit и push папки `docs/` в публичный репозиторий). Для проверки без публикации — `run`, затем `brief`.
- `python -m planner run` — только расчёт и дашборд (без ИИ и без публикации).
- `python -m planner brief` — только ИИ-сводка и пересборка дашборда.
- `python -m planner publish` — только публикация и уведомление.
- `python -m planner sku SKU-XXXXXX` — полный расчёт по одному товару (JSON).
- `python -m planner run --asof 2026-08-13` — задать дату среза вручную, если в имени выгрузки её нет (данные не обрезаются).
  Дата должна попадать в неполный месяц выгрузки, иначе расчёт остановится с кодом 2.
- `python -m pytest tests` — тесты; запускать после любой правки кода расчёта.
- Коды возврата: 0 — успех, 1 — не удалась публикация, 2 — выгрузка не годится для расчёта (`DataError`).

## Данные
Выгрузка ERP: `sku_dim`, `sales_monthly`, `stock_monthly`, `purchase_orders`, `receipts`, `supplier_dim` (описание — `data/raw/README.md`).
Новая выгрузка: положить zip в `data/inbox/` — `run` сам распакует самый свежий в `data/raw/`.
Дата среза берётся из имени zip (`..._YYYYMMDD.zip`).

## Правила интерпретации (важно)
- Последний месяц выгрузки неполный: в оценку спроса не идёт, но учитывается в остатке.
- Нет строки в `stock_monthly` = остаток 0.
- Месяц, к концу которого товар кончился, — дефицитный: продажи там занижены, в оценку спроса не берём.
- Открытый PO с прошедшей датой: до 60 дн. просрочки считаем «едет», старше — не учитываем и показываем к проверке.
- Наценка < `min_markup_pct` → не закупаем автоматически, список «Пересмотр цены»; в риски дефицита такие позиции не входят.
- Пустая наценка при наличии продаж = нет себестоимости в ERP (а не «не продавался», как сказано в README выгрузки) → в плане, но с пометкой «проверить наценку».
- Нет продаж `dead_months` мес. (сейчас 12) → мёртвый ассортимент, не закупаем.
- Вес заполнен у единиц SKU — расчёт контейнеров не делаем, сообщаем как проблему данных.
- ABC считается внутри категории: дециль цены в выгрузке задан внутри категории, между категориями он несравним.
- Категории без выраженного сезона (пик индекса ниже `flat_season_below`) прогнозируются ровно, без сезонности.
- Объём кратен партии из истории заказов; если партия больше годового спроса — объём не округляется, позиция помечается «согласовать партию».
- Дата среза должна попадать в неполный месяц выгрузки; выгрузка старше `stale_days` — предупреждение на дашборде и в сводке.
- Бэктест сравнивает прогноз с фактом только там, где продажи показывают спрос: товар не кончился и на складе было
  не меньше `min_avail_share` обычного спроса месяца. В оценку спроса второе условие не идёт — у медленных товаров оно вредит.

## Как проверять результат после запуска
1. KPI не прыгнули без причины (блок «Что изменилось» сравнивает с прошлой выгрузкой; повторный запуск на тех же данных его не сбрасывает).
2. Топ-10 «заказать сейчас» по объёму: объём ≈ спрос на (плечо + цикл) + страховой − остаток − в пути. Смотри `python -m planner sku`.
3. Сезонные категории: обогреватели не заказываются так, чтобы приходить после сезона; триммеры — заказ под май.
4. Аномалии в данных (огромное «в пути» при малом спросе, просроченные PO, пустой поставщик) — в сводку закупщику.

## Стиль общения с закупщиком
Коротко, по делу, на русском, с кодами SKU и числами из расчёта. Сначала действие, потом причина.
