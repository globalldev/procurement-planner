# ИИ-система планирования закупок

Импортёр электроинструмента, садовой техники и сантехники из Китая, плечо поставки 4–6 месяцев.
Система по выгрузке ERP отвечает на вопросы закупщика:

- **что** заказать и **сколько** — по каждому SKU, с округлением до кратности партии;
- **на сколько хватит** текущих запасов с учётом заказов в пути;
- **когда** размещать следующий заказ — календарь на 12 месяцев;
- где **риск дефицита** (не успеем довезти) и **избытка** (заморожены деньги);
- что убрать из автозакупки: низкая наценка (< 25%) и мёртвый ассортимент.

**Дашборд:** https://globalldev.github.io/procurement-planner/

Результат — дашборд (`docs/index.html`), Excel для закупщика (`out/plan.xlsx`) и короткая сводка, которую пишет ИИ-агент.

## Как устроено

```
data/inbox/*.zip ──► planner (Python, детерминированный расчёт) ──► out/plan.json, plan.xlsx
                                                                   │
                         prompts/buyer_brief.md ──► claude -p ◄────┘  (ИИ читает расчёт, пишет сводку)
                                                                   │
                                     dashboard/template.html ──► docs/index.html ──► хостинг + Telegram
```

**Разделение ролей.** Числа считает код: прогноз, проекция остатков, даты и объёмы. ИИ (Claude Code) управляет
циклом — принимает данные, запускает расчёт, проверяет результат на здравый смысл, находит аномалии в данных,
объясняет рекомендации и пишет сводку. Так модель не может «придумать» объём заказа, а каждая цифра воспроизводима.

### Логика расчёта
1. **Спрос, а не продажи.** Месяц, к концу которого товар закончился (остаток на 1-е + приходы − продажи ≈ 0),
   не используется для оценки спроса — продажи там занижены.
2. **Прогноз = уровень × сезонность.** Сезонный профиль категории по 5 годам, уточнённый историей SKU;
   у категорий без выраженного сезона (смесители, зернодробилки) спрос считается ровным — так точнее на бэктесте.
   Уровень — взвешенное среднее за 12 мес. (свежие весят больше); разовые оптовые отгрузки срезаются.
3. **Проекция остатков по дням** на 18 мес.: остаток сейчас + открытые PO на даты прихода − прогноз.
   Просроченные PO до 60 дней считаем едущими, старше — не учитываем и показываем к проверке.
4. **Дата заказа** = день, когда остаток упадёт ниже страхового запаса, минус плечо (медиана PO поставщика → история SKU →
   справочник поставщика → норматив; плюс 14 дн. на задержку, итого ≤ 180 дн.). Сезонные товары не заказываются с приходом в мёртвый сезон.
5. **Объём** = спрос на 90 дней после прихода + страховой − ожидаемый остаток − что ещё приедет, с округлением вверх до партии
   из истории заказов. Если партия больше годового спроса, объём не раздувается, а позиция помечается «согласовать партию».
   Страховой запас по ABC (95/90/85%), масштабируется по сезону; ABC считается внутри категории, потому что дециль цены
   в выгрузке задан внутри категории и между категориями несравним.
6. **Проверка прогноза на истории** (бэктест, три точки отсчёта). В проверку идут только месяцы, где продажи показывают спрос:
   товар не кончился и на складе было не меньше половины обычного спроса месяца (иначе 1–10 шт остатка при спросе в сотни
   считались бы «товар был»); таких месяцев ~51%. WAPE по кварталу на последнем годе — 53% против 91% у «среднего за 12 мес»
   и 60% у «как год назад»; на точках 18 и 24 мес. назад — 36–37% против 69–77% и 46–47%. Смещение прогноза — от +5% до −11%:
   систематического завышения нет.
7. **Ловушки в данных, которые система обрабатывает явно:** пустая наценка у 46 продающихся SKU — это нет себестоимости,
   а не «не продавался» (в плане с пометкой); 2 292 шт в зависших PO не считаются едущими; вес заполнен у 7 SKU из 791;
   у 328 из 603 закрытых PO нет привязанного прихода. Всё это — в блоке «Качество данных» на дашборде.

Все параметры — в `config.toml`.

## Запуск

```bash
pip install -r requirements.txt
python -m planner all           # расчёт + ИИ-сводка + дашборд + публикация (commit и push только папки docs/)
python -m planner run           # только расчёт и дашборд, без публикации
python -m planner sku SKU-197B08
python -m pytest tests          # тесты расчёта на синтетической выгрузке (или python -m unittest discover -s tests -t .)
```

Новая выгрузка: положить zip в `data/inbox/` → `python -m planner all`. Дашборд покажет, что изменилось с прошлой выгрузки
(повторный запуск на тех же данных сравнение не сбрасывает).

Защита от неверных данных: дата среза должна попадать в неполный месяц выгрузки, иначе расчёт останавливается (код возврата 2)
и ничего не публикует; выгрузка старше `data.stale_days` помечается на дашборде и в сводке. Сбой публикации — код возврата 1.
Ежедневно: `powershell -File scripts/install_schedule.ps1 -At 07:00` (Планировщик Windows).
Демо «выгрузка через неделю»: `python scripts/demo_next_drop.py 2026-08-20`.

## Claude Code
- `CLAUDE.md` — роль агента, структура, правила интерпретации данных, чек-лист проверки результата.
- `.claude/skills/procurement-run` — полный цикл с проверкой здравого смысла (`/procurement-run`).
- `.claude/skills/sku-explain` — разбор рекомендации по товару (`/sku-explain SKU-…`).
- `.claude/skills/what-if` — сценарии: «что если поднять уровень сервиса / изменить цикл».
- `prompts/buyer_brief.md` — промпт ИИ-сводки; запускается headless через `claude -p` без инструментов.
  Числа, проценты, даты и коды сводки сверяются с расчётом; при расхождении на дашборд идёт автосводка,
  а отклонённый текст остаётся в `out/ai_brief_rejected.md`.
